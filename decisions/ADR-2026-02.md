# ADR-2026-02: Tiered Release Practices Across All Greenmark Repos

- **Status**: Accepted
- **Date**: 2026-04-10
- **Owner**: Daniel Shanklin / Director of AI & Technology
- **Related**: `tools/tier-map.sh`, `tools/bootstrap-repo.sh`, `tools/ensure-release.sh`, `ADR-2026-01`
- **Navigation**: [← Cockpit README](../README.md) · [Tools Index](../tools/README.md) · [All Decisions](README.md)

## Context

Greenmark runs 13 repos across a spectrum from production dashboards to reference documentation. Until now, release practices were applied ad-hoc — some repos got CI, some got branch guards, most got nothing. The February develop-branch-deletion incident (cerebro-migrations) exposed the gap: we had no systematic way to enforce or even audit what protections each repo had.

A one-size-fits-all approach doesn't work here. Production apps need deploy gates and code review. Internal tools need CI. Docs repos need almost nothing. Applying enterprise ceremony to a docs repo wastes time; applying docs-level ceremony to a production app risks outages.

## Decision

**Classify every repo into one of three tiers and apply tier-appropriate release practices automatically via a single bootstrap script.**

| Tier | What | Repos | Ceremony |
|------|------|-------|----------|
| **T1 Production** | Real users see these, outages page people | cerebro, cerebro-migrations, data-daemon | CI, deploy workflows, PR template, CODEOWNERS, dependabot (human review), branch protection, pre-push hooks |
| **T2 Supporting** | Internal tools, QA, analytics | cerebro-qa, cerebro-warp-speed, cerebro-warp-speed-excel, cerebro-ai-services, cerebro-bot-farm | CI, PR template, dependabot (auto-merge patches), pre-push hooks |
| **T3 Reference** | Docs, config, research | infra, greenmark-cockpit, cerebro-mcp, cerebro-vault, cerebro-excel | Pre-push hooks only |

The classification lives in one file (`tools/tier-map.sh`). When a repo changes tier, you edit one line and re-run the auditor.

Deploy workflows are NOT bootstrapped — they're repo-specific (Railway for cerebro, Supabase for cerebro-migrations, etc.) and require per-repo configuration. The bootstrap handles everything that CAN be standardized.

## Rationale

- **The forcing function is classification, not tooling.** The act of assigning tiers forces you to decide what matters. Everything else flows from that decision.
- **One script, one source of truth.** `bootstrap-repo.sh` reads the tier and applies the right level. `ensure-release.sh` audits all repos against their tier and reports drift. No manual checklist to maintain.
- **Matches the team.** 1 human + AI agents. Enterprise ceremony (semantic-release, changelog automation, CONTRIBUTING.md) solves problems we don't have yet. PR templates with "Why?" and "How tested?" solve problems we have now.
- **Idempotent and safe.** Both scripts skip what already exists. Re-running is free.

## Options Considered

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **A. Tiered bootstrap (chosen)** | Classify repos, apply tier-appropriate practices via script | Right-sized for each repo, single source of truth, auditable | Must maintain tier-map when repos are added |
| B. Uniform enterprise | Same practices on all 13 repos | Consistent, no classification needed | Over-gates docs repos, wastes CI minutes, review fatigue on T3 PRs |
| C. Per-repo manual | Each repo configured individually | Maximum flexibility | No consistency, no auditability, things drift silently |
| D. Monorepo | Consolidate into one repo | One CI, one set of rules | Repos serve different purposes (app vs pipeline vs docs), deployment coupling, Supabase CLI expects its own repo |

## What We Explicitly Skipped (and When to Revisit)

| Practice | Why skipped | Revisit when |
|----------|-------------|-------------|
| Semantic-release / changelog automation | Earns its complexity at 5+ humans or 50+ releases/month | Team grows past 3 developers |
| CONTRIBUTING.md | One developer knows the rules | Second external contributor joins |
| Code coverage gating | No test suite is mature enough to gate on coverage | Any repo hits 60%+ coverage organically |
| Branch protection via API | GitHub free plan returns 403 on private repos | Org upgrades to GitHub Pro/Team |
| Auto-merge workflow for T2 dependabot | Labels are set, but no workflow consumes them yet | Dependabot PRs start piling up unmerged |

## Implementation

Three files in `greenmark-cockpit/tools/`:

| File | Purpose |
|------|---------|
| `tier-map.sh` | Associative array mapping repo name → tier. Sourced by both scripts. |
| `bootstrap-repo.sh` | Applies tier-appropriate artifacts to a single repo. Idempotent. |
| `ensure-release.sh` | Audits all repos against tier-map, reports drift. `--apply` fixes gaps. |

To bootstrap all repos: `./tools/ensure-release.sh --apply`
To audit without changing anything: `./tools/ensure-release.sh`
To add a new repo: add it to `tier-map.sh`, re-run `ensure-release.sh --apply`

## Consequences

- **Positive**: Every repo has explicit, auditable, tier-appropriate release practices. Drift is detectable and fixable in one command. New repos get bootstrapped in seconds.
- **Negative**: The tier classification is a judgment call. A repo that's "T2 today but T1 next month" needs a human to upgrade it. The scripts don't auto-detect production-ness.
- **Neutral**: Deploy workflows remain per-repo. This is intentional — Railway, Supabase, and "no deploy" are too different to template.
