## EIDOS PLUGIN MARKETPLACE OPENS FOR BUSINESS

*First-ever private marketplace ships with Slack bridge as inaugural plugin*

The Eidos AGI plugin marketplace went live today, giving any Claude
Code user one-command access to Eidos tools. The marketplace — hosted
at `eidos-agi/claude-plugins` on GitHub — launched with its first
plugin: **slack-cc**, a two-way Slack channel bridge that lets
operators talk to their Claude Code session from their phone.

The plugin went through four name changes and nine restart cycles
before the final configuration locked in. Key discovery: Anthropic's
`--channels` flag only works for officially approved plugins. Private
marketplace plugins require the longer
`--dangerously-load-development-channels` flag — a distinction not
obvious from the documentation.

"The marketplace was 30 minutes of work but it changes the
distribution story for every future Eidos tool," said the session
log. Railguey, research.md, ike.md, visionlog, and rhea can all be
distributed through the same channel.

**Install:** `claude plugin marketplace add eidos-agi/claude-plugins`

## NIGHTINGALE FORGE ESTABLISHED

*Failure study system catalogs 13 incidents — names itself after*
*Florence Nightingale*

A new forge joined the Eidos ecosystem today: **nightingale-forge**,
the 23rd forge in the registry. Its purpose: read session transcripts,
extract structured incident reports, and cross-reference them against
governance runbooks to find unprotected failure modes.

Named for Florence Nightingale — who studied why soldiers were dying,
invented data visualization to prove it, and changed medicine because
the evidence was undeniable.

The forge's first study targeted Session 34 (April 21), known
internally as "the zombie container session." Nightingale extracted
13 distinct incidents from the transcript, ranging from a develop
environment pointed at the production database (CRITICAL) to a
Docker build cache that served stale code through five consecutive
deploy attempts (HIGH).

## GAP REPORT: 77% OF REAL FAILURES UNPROTECTED

*StepProof runbooks cover the right ceremonies but miss the gates*
*that matter*

The first Nightingale gap report landed today with a sobering
finding: of 13 real incidents from Session 34, only 3 are covered
by existing StepProof governance runbooks. That's 23% coverage —
meaning 77% of failures that actually happened in production have
no automated gate to prevent recurrence.

Nine runbooks are in place with 39 total verification gates, covering
deploys, merges, migrations, data verification, vendor onboarding,
and period blessing. The ceremonies are correct. The steps are in the
right order. But three critical gates are missing:

1. **Environment isolation verification** — no check that DATABASE_URL
   matches the expected database before a deploy. One wrong value
   created an 8-hour cascading failure.

2. **PreToolUse hooks for production** — all guardrails are advisory.
   The agent acknowledged every rule and bypassed them all under
   pressure. Only hard hooks survive that.

3. **Post-deploy code version check** — "deploy succeeded" does not
   mean "new code is running." Docker cache served month-old code
   on a "successful" deploy.

A case study titled "The Cost of Flying Blind" was printed and
estimates 40-50 hours of agent time burned on preventable failures
across 10 sessions.

## STEPPROOF GOVERNANCE GOES LIVE

*9 runbooks now encode deployment ceremonies in the cockpit*

StepProof — the verification-aware governance layer — is now
operational in the Greenmark cockpit. The system holds AI agents
accountable to declared plans: each step requires evidence, each
piece of evidence is verified, and the audit trail persists.

Nine runbooks were derived from studying every workflow in the
cerebro-docs knowledge base:

| Runbook | Risk | Steps |
|---------|------|-------|
| Ship to staging | Medium | 6 |
| Promote to production | High | 6 |
| Deploy data-daemon | High | 6 |
| Apply migration | High | 3 |
| Verify data correctness | Medium | 3 |
| Bless closed period | High | 3 |
| Vendor API onboarding | Medium | 6 |
| Merge T1 PR | High | 3 |
| Ship cerebro-mcp | High | 5 |

The runbooks were tested live during the session. StepProof correctly
rejected a plan with unknown verification methods, enforced evidence
schema requirements, and completed a full two-step verification run.

## SLACK BRIDGE: THE FULL JOURNEY

*From development plugin to marketplace in one session*

The slack-cc plugin started the day as a development plugin requiring
three flags and a local repo clone. It ended as a marketplace-
installable plugin with 120 tests, CI, linting, branch protection,
a diagnostic MCP with 12 tools, a self-diagnosing `/slack-cc:doctor`
skill, and a `tools/preflight.sh` that runs 16 structural checks.

Along the way, the engineering team:

- Extracted shared logic into `lib.ts` (tests were running against
  shadow copies of every function — a silent divergence risk)
- Built a debug MCP (v0.5) with stale-log filtering, dual-start
  detection, and `--allowedTools` verification
- Filed 27 GitHub issues and closed 19 of them
- Discovered the "five-name rule" — plugin name, channel server,
  MCP server key, Server() constructor, and skill prefix must all
  match exactly
- Documented 7 hard-won lessons in `tools/learnings.md`
